- [x] **T01**: Check that the built behaviour of row `app-create-from-spreadsheet` meets REQ-BQCV-001 in `data-import-wizard`; add a test that asserts each scenario, and close any gap the scenarios name.
  - Gap left (20 Nov, decision): the create-app wizard has no "Start from a spreadsheet" option; importing a file exists only after the app exists (`ImportDataWizard`). Options: A frontend create-import-pages with delete on failure; B a server-side `fromFile` wizard step with real rollback; C validate the file first, then A or B. Recommended B.
  - Decided (24 Nov, lane): B, a server-side `fromFile` step. It is the only option that meets "a file that cannot be read creates nothing", because the wizard's existing rollback (`ApplicationCreationService::rollback()`) already removes the Application, its versions and their registers on any failed step, while A leaves a window where a half-made app exists and depends on the browser staying open. Plan for the build, in this order:
    1. The wizard's step 1 offers "Start from a spreadsheet" beside "Start from a database" and sends the file with the payload as `fromFile: {name, mime, content (base64)}` (CSV, XLS, XLSX; refused above OpenRegister's import limit before anything is created).
    2. `validatePayload()` checks `fromFile` (extension, mime, size, a readable header row) and returns it on the plan, as it does for `fromDatabase`.
    3. A step after `createVersions()` imports the file into the first version's register through OpenRegister's register import with schema inference (the same call `ImportDataWizard` makes for "as a new schema"), records the created schema on `$state`, and on any import error calls `rollbackAndThrow(failedAtStep: 'import-file')`, so the wizard shows the import error and nothing remains.
    4. The first version's manifest gets a list page and a detail page bound to the new schema, the list page first so the app opens on it (the pages `fromDatabase` writes per table).
    5. PHPUnit for 40 rows with name, address and status (one schema with those fields, 40 records, list and detail pages) and for an unreadable file (nothing left after rollback); Vitest for the step 1 option; an e2e spec written to run in the nightly.
  - Built (24 Nov, plan B): wizard step 1 has "Start from a spreadsheet" (`StartFromSpreadsheet.vue`, CSV/XLS/XLSX up to 10 MB, excludes "Start from a database") and posts `fromFile: {name, mime, content}`. `SpreadsheetAppSource` checks the file before anything is created (type, size, a header row with no empty or repeated column names; XLSX read with ZipArchive, XLS with the spreadsheet library OpenRegister ships, else refused with "save as XLSX or CSV") and makes one exportable schema with a text field per column. `ApplicationCreationService` seeds that schema into every version's register, gives every version a list page (first, opened by the menu) and a detail page for it, and in the new `import-file` step loads the rows into the first version's register through OpenRegister's `ObjectImporterInterface` (`importFromCsv`/`importFromExcel`). An import that throws or refuses any row rolls everything back: the import job is undone, the schema, registers, versions and app are deleted, and the wizard shows the import error. PHPUnit `tests/Unit/Service/SpreadsheetAppSourceTest.php`, `tests/Unit/Service/ApplicationCreationFromFileTest.php`; Vitest `tests/dialogs/CreateApplicationWizard/StartFromSpreadsheet.spec.js`; e2e `tests/e2e/create-app-from-spreadsheet.spec.ts` written, runs in nightly.
